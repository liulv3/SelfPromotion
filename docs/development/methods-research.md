# 项目管理方法调研与最小采用方案

核验日期：2026-10-23。范围：现有单用户科研工作台的文档入口、目录和上下文管理；以下是建议与来源核验，不代表软件功能已经实现。采用 agent-reach 检索流程及 OpenAI Docs，网页搜索与阅读使用当前已连接的搜索工具；未安装新 Skill 或管理框架。

## 五组一手方法，按当前采用价值排序

| 方法与来源 | 本项目采用什么 | 暂不采用什么 / 局限 |
|---|---|---|
| **1. OpenAI：AGENTS.md 指令发现** — [官方指南](https://learn.chatgpt.com/docs/agent-configuration/agents-md) | 根文件用标准名 `AGENTS.md`，只放简介、关键约束和文档导航；局部有特殊约束时再增加子目录指令 | `AGENT.md` 不是默认发现名称，需自定义 fallback 才能识别，因此不维护两份核心正文。根会话不会启动时自动扫描所有子目录；修改模块前仍需检查该路径上的局部指令 |
| **2. OpenAI：Skills 渐进式披露** — [官方说明](https://learn.chatgpt.com/docs/build-skills) | 借鉴“先名称和简述，使用时才读完整内容”的模式：根入口 → 任务索引 → 当前目标所需的 1–3 份文档 → 必要附录 | 普通 Markdown 索引不会自动获得 Skill 的加载机制，必须在根指令中写明读取规则。暂不为每份产品文档创建 Skill；只有重复、稳定的操作流程再封装 |
| **3. Nygard：架构决策记录 ADR** — [作者原文](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions) | 每个重要选择一份短 Markdown：状态、背景、选择、代价、替代方案；被新决策取代后保留旧文并链接替代项 | 不把每次讨论、命名调整都变成 ADR；不引入 ADR 管理平台。适合记录“本地单体”“Zotero 只读”“单一正式知识库”等会影响后续实现的决定 |
| **4. Cookiecutter Data Science：数据隔离与原件不可变** — [官方设计原则](https://cookiecutter-data-science.drivendata.org/opinions/) · [项目](https://github.com/drivendataorg/cookiecutter-data-science) | 源代码与个人研究数据分离；论文原件不被解析流程覆盖；中间结果可重建；数据和密钥默认不进源码 Git | 不整套生成数据科学模板，不强制 notebooks、模型训练和云存储目录。其处理流水线的 DAG 思想用于产物血缘，不能据此把本项目所有技术关系强制成树 |
| **5. Diátaxis：按读者需求写文档** — [官方入门](https://www.diataxis.fr/start-here/) | 区分“怎样完成任务”“接口事实”“为什么这样设计”和“上手练习”；索引标注阅读目的，避免一篇文件混杂全部内容 | 当前不强行建立四大文档站，也不安装 Docusaurus/MkDocs。先改善现有文件的用途和导航，有真实需要再增长 |

## 最小落地方式

**一个入口、一个索引、少量权威文档。** `AGENTS.md` 建议控制在约 60–100 行以内（本项目建议，非官方限制），写明项目目标、当前阶段、证据可追溯/AI 草稿与确认知识的边界、个人数据不入 Git、改动如何验证。细节进入 `docs/`，用索引将用户目标映射到指定文件；不要要求每次会话先阅读全部方案与历史讨论。

索引每项包含“何时读取、文档用途、权威级别/状态”。例如：做 Zotero 接入时读取当前架构及文献模块契约；改精读时读取解读契约及质量门槛；做 Git 发布时读取开发流程。当前裁决优先于历史研究材料；当裁决变化时更新相应正文与索引，历史会议资料只作背景。

**保持现有架构对应的目录分工。** `docs/` 存产品、架构、选型、开发和验收文档；`apps/` 存工作台与后端/任务执行代码；`packages/` 只在确有共享契约或组件时使用；`tests/` 存测试和获准公开的小样本；`scripts/` 存可重复的开发辅助脚本。目录代表代码边界，不意味着新增微服务。

**个人资料与公开仓库有明确边界。** Zotero 继续保存已有文献权威原件，本项目保存条目/附件引用；独立导入的 PDF、解析结果、数据库文件/导出、索引、运行日志和生成报告进入本地数据目录并默认忽略。精确目录名由项目目录规范统一，不在多个指南重复定义。可以提交无隐私的配置样例和可再分发测试样本；不能仅因扩展名是 `.md` 就将私人论文笔记默认提交。首次 Git 提交前检查被跟踪清单，忽略规则不会自动移除已经跟踪的文件。

**只加必要的管理约束。** 开发文档与代码一起版本管理；复杂任务保留短计划和验收结果，跨会话只更新当前状态/下一步；影响边界的选择写 ADR。暂不引入完整 GitFlow、额外任务管理系统、独立图数据库或第二套领域存储，也不自动生成一批 Skill；沿用上游 SurrealDB 不受此限制。后续有真实痛点，再增加局部 `AGENTS.md` 和适配当前实现的 CI。本轮已增加轻量文档链接与跟踪边界检查脚本。

本页提议的行数、目录分工与阅读顺序是针对本项目的综合判断，不是上述资料的强制标准。
